## 概念回答
什么是微服务架构？

微服务架构是一种按业务能力把系统拆成一组小型服务的做法。每个服务只负责一块相对完整的业务，比如订单、支付、库存，能够独立开发、测试、部署和扩展，通常也尽量独立管理自己的数据，服务之间通过 HTTP、gRPC 或消息队列这类轻量方式通信。它并不是单纯把代码拆小，而是希望通过清晰的业务边界和团队分工，让系统更容易演进，但同时也带来网络调用、分布式事务、监控和运维上的新问题。

微服务和单体架构的主要区别是什么？

微服务和单体架构最大的区别，在于系统的组织方式和运行方式不同。单体通常是一个代码库、一个部署单元，模块之间直接函数调用，常常共用一个数据库，扩展时基本是整体一起扩，初期开发简单，但时间久了容易耦合。微服务则是多个独立部署的服务，通过网络通信，各自管自己的数据，可以按需扩展，也能隔离部分故障，但代价是系统更复杂，对自动化部署、监控和团队协作的要求更高。

为什么本课程先实现单体系统，再逐步拆分为微服务？

主要是为了让你先看清业务和领域模型，而不是一上来就被服务发现、网关、配置中心、分布式事务这些基础设施拖住。很多服务边界不是设计出来的，而是在代码和需求变化中慢慢暴露出来的，过早拆分很容易拆成“分布式单体”，看着服务很多，实际还得一起改、一起发。先做单体再演进，既能跑通核心流程，也能让你真正体会拆分的理由和代价。

为什么作业需要提供可重复运行的测试或验证脚本？

是为了让结果不依赖某台电脑、某个人的操作习惯或口头描述。别人拿到代码后，按脚本就能验证接口、输入输出和边界情况，修改代码时也能及时发现旧功能有没有被破坏，评分和反馈会更客观。这其实是在培养一种工程习惯：系统不仅要能跑，还要能用可执行的方式证明它一直能跑。

项目选题
1. 项目名称
宠医通（PetCare）宠物医院管理系统

2. 业务背景与要解决的问题
城市养宠家庭增多，宠物医院普遍存在：

预约靠电话/微信，容易冲突、漏约；

宠物病历分散，医生难以连续跟踪；

处方、药品库存、收费脱节；

复诊提醒、候诊叫号依赖人工；

多角色协作效率低。

本项目目标是构建一个覆盖“预约—接诊—病历—处方—发药—收费—复诊提醒”的宠物医院管理系统。

3. 主要目标用户及需求
角色	主要需求
宠物主人	注册登录、管理宠物档案、预约医生、查看病历、缴费、接收提醒
医生/兽医	查看排班、接诊、填写病历、开处方、查看历史病历
前台/护士	预约管理、到院签到、候诊叫号、收费
药房/库管	药品目录、库存管理、处方发药、库存预警
管理员	用户与角色管理、医生排班、收费项目、统计报表
4. 选择该题目的原因
多角色明确，适合做认证、授权与 RBAC；

业务模块边界清晰，天然适合后续服务拆分；

有预约冲突、处方扣库存、收费与账单一致性等事务场景；

有预约提醒、候诊叫号、收费成功、复诊提醒等消息场景；

支付可模拟，不依赖真实物流、保险、短信，复杂度可控；

业务闭环完整，适合一学期持续演进。

5. 初步边界
当前只做单院区核心诊疗闭环：用户、宠物、预约、病历、处方、药品、收费、通知、统计。
暂不纳入多院区连锁、真实支付、保险理赔、医学影像 AI、第三方配送等外围能力。


功能规划
1. 角色与权限
宠物主人：管理自己的宠物、预约、查看病历与账单；

医生：接诊、写病历、开处方；

前台：预约、签到、候诊、收费；

药房：发药、扣库存、库存预警；

管理员：用户、角色、排班、收费项目、统计。

权限模型采用 RBAC：用户—角色—权限—资源。

2. 功能模块划分
模块	具体功能
认证与权限	注册、登录、JWT、角色权限控制
宠物与主人档案	主人信息、宠物信息、疫苗、过敏史
预约与排班	医生排班、时间段预约、取消/改期、冲突检测、签到、候诊队列
门诊病历	接诊记录、症状、诊断、医嘱、处方、历史病历
药品与库存	药品目录、库存数量、处方扣减、低库存预警
收费与账单	收费项目、生成账单、模拟支付、退款/作废、收费记录
通知	预约成功、候诊叫号、收费成功、复诊提醒
统计报表	门诊量、医生工作量、收入统计、药品消耗
3. 核心业务流程
主人注册登录，添加宠物档案；

选择医生和可预约时间段；

系统检查排班与预约冲突，预约成功；

发送预约成功提醒；

主人到院，前台签到，进入候诊队列；

医生接诊，填写病历并开具处方；

药房发药，扣减库存；

前台生成账单，主人模拟支付；

系统记录收费成功，发送复诊提醒；

主人查看病历、处方和账单。

4. 当前项目范围与暂不实现
本期实现：单院区、核心诊疗闭环、模拟支付、站内通知、基础统计。
暂不实现：真实支付、保险理赔、多院区、真实短信/微信推送、医学影像 AI、复杂财务审计、药品配送。

5. 后续演进方向
认证鉴权：Spring Security + JWT；OAuth2 作为统一认证中心；RBAC 做权限；服务间优先透传用户 JWT。

持久化：MySQL/PostgreSQL 存业务数据，Redis 做缓存/预约锁；对象存储用RustFS。

服务拆分：用户宠物服务、预约排班服务、病历服务、药品库存服务、收费账单服务、通知服务。

消息：RocketMQ/Kafka 处理预约提醒、收费成功、库存扣减、复诊提醒。

事务：本地事务处理收费/账单;最终一致性处理处方—库存—收费等跨服务流程。

监控：Actuator、SkyWalking。

部署：Docker Compose 本地部署 CI/CD。
